## 1. Ownership and purpose

This repository owns the Solar/FoxESS project outcome, source evidence, requirements, specifications, acceptance criteria and accepted product artefacts.

The separate [Rio AI Harness](https://github.com/riosystems/rioit-ai-harness) may execute this work as its first proving project. The Harness owns the bounded execution lifecycle, authority application, context materialisation, assignments, review handoffs, durable gates, execution evidence and economics. It does not own or absorb the Solar/FoxESS specification.

The proving work exists to test whether the Harness can execute a real bounded document workflow without coupling either product to the other.

## 2. Candidate project work order

The representative outcome is to produce or revise a bounded, read-only tenant-zero FoxESS capability artefact from an approved successor to the candidate capability specification.

Before authorisation, the project must identify the exact:

- Work Order Revision and expected deliverable;
- specification and acceptance criteria;
- frozen Solar and vendor evidence cut;
- read-only Authority Envelope Revision;
- resolved governance baseline;
- author, independent reviewer and human acceptance responsibilities;
- effort, elapsed-time, API-quota and interruption bounds;
- publication destination in Solar's durable project truth.

The project-specific work order is supplied to the Harness through its provider-neutral proving-work contract. It is not embedded in the Harness product specification.

## 3. Path A: departure resolved during specification

Assume a future applicable Law requires an existing mechanism to be extended rather than introducing a second mechanism where safe.

During specification, the existing generic provider mechanism is found to permit arbitrary requests. That makes the spike's exact read-only method/path allow-list difficult to enforce or prove. The project specification proposes a narrow, disposable spike mechanism.

Governance approves a tightly scoped departure before implementation. It permits only:

- this project work-order and specification revision;
- the enumerated read-only calls;
- tenant-zero evidence gathering;
- no generic request facility;
- no control endpoint or state change;
- no production adapter or reusable architecture decision.

Compensating controls include capability restrictions, brokered credentials, secret removal, request/response provenance, independent boundary review and expiry at completion or supersession.

The departure is embedded in the resolved governance baseline supplied with the project work order. It may constrain execution further, but it cannot expand the project Authority Envelope or weaken intrinsic Harness platform constraints.

### Expected Harness behaviour

- The build assignment may exercise the departure without another prompt.
- The Harness records when and how it was exercised.
- Review verifies that execution remained inside its scope.
- Any activity outside that scope remains prohibited.
- Expected post-authorisation interruption count: zero.

The departure is already governed work. Reconfirming it would be an unnecessary human interruption.

## 4. Path B: conflict discovered during execution

Assume a future applicable Law requires tests to exercise inputs and routes the real system can produce.

The project specification asks the spike to observe simultaneous solar export and grid battery charging naturally, or report that it was not observed. During execution:

- the implementation and ordinary tests complete;
- every call remains read-only;
- the condition does not occur within the observation window;
- synthetic tests prove handling but cannot establish tenant-zero reality;
- deliberately causing the condition requires control activity outside the specification and Authority Envelope;
- forecast compliant effort exceeds the remaining approved bounds.

This is new project evidence, not permission to ignore the rule or claim success.

### Governance conflict

The Harness records one durable Governance Conflict containing:

- exact project work-order, assignment, attempt and baseline identities;
- affected rule and acceptance criterion;
- facts and evidence discovered;
- compliant approaches attempted;
- actual and forecast resource consumption;
- remaining compliant options;
- any precise proposed departure;
- risks, compensating controls and consequences.

The assignment pauses without timeout. Further observations of the same scenario enrich the same conflict rather than prompting again.

### Available project/governance resolutions

1. **Approve a scoped departure.** A new governance baseline permits a precisely described result, such as retaining “not observed” with synthetic handling tests and requiring later live verification before production acceptance.
2. **Continue with the Law in force.** Extend or redirect effort, provide an appropriate environment, or otherwise pursue compliant evidence. This may revise budget, schedule or assignment but grants no departure.
3. **Return to specification or stop.** Narrow the claimed outcome, defer the affected capability or end the work while retaining all paid-for evidence.

No resolution converts missing or unverified evidence into Pass.

## 5. Non-departable constraint variant

If an applicable non-departable constraint prohibits deliberate device control, an ordinary work-order decision cannot waive it.

If control is the only practical way to produce the condition, the work returns to Solar specification and governance. Valid outcomes are limited to those authorised by the governance provider: change the project outcome, establish a permitted non-applicability route, change governing policy through its proper lifecycle, or stop.

## 6. State transitions

The successful pre-resolved path is:

> project specification resolution → Harness-ready work order → implementing → completed under approved departure → review → Solar acceptance

The newly discovered path is:

> project specification resolution → Harness-ready work order → implementing → paused for governance decision → resumed under exact resolution, superseded or stopped

The pause is caused by a newly evidenced boundary crossing, not by normal implementation choices.

## 7. Durable information homes

- **Solar Optimiser repository:** accepted project specifications, implementation and product artefacts.
- **Solar project issues/records:** requirements, project decisions, acceptance and useful summaries.
- **Harness execution evidence:** assignments, attempts, exact execution inputs, review evidence, durable gates and resource telemetry.
- **Task-scoped Sandbox:** disposable materialised context and intermediate working state.

Nothing required to understand, build, test, operate or maintain the accepted Solar result may remain only in the Harness ledger or Sandbox.

## 8. What the proving work should establish

- Governance resolution normally belongs in project specification/readiness work.
- A pre-approved departure is evidence-bearing authority, not a future prompt.
- Reasonable effort is evaluated against explicit project bounds and forecasts.
- Continuing with a constraint differs from approving a departure.
- Non-departable constraints cannot enter an ordinary exception route.
- Resumed work binds the exact decision and resulting revisions.
- One material conflict causes at most one durable human interruption.
- The Harness can execute the work without becoming the owner of its project truth.

## 9. Decisions required before authorisation

- Select the exact FoxESS source/evidence cut.
- Select the exact new or revised project artefact to produce.
- Approve its acceptance criteria and read-only authority boundary.
- Resolve the applicable governance baseline and any known departures.
- Set effort, quota, contingency and escalation bounds.
- Select the author and independent reviewer configurations.
- Select the Solar publication destination.
